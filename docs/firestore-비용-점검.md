# Firestore 읽기 비용 점검

점검일: 2026-10-21  
범위: 후기 목록, 상품(리조트) 카드, 상세 화면 + 로그인 후 전역 구독  
기준: 일반 다이버(비관리자). 코드 변경 없음(점검만).

## 한 줄 요약

- **상품 카드 / Explore / 상세의 별·좌석·상품** → 로그인 시 켠 `shops` **실시간 감시**를 메모리에서 재사용 → **화면만 열면 추가 읽기 0**
- **후기 글 목록** → 상세에서만 **1회 get**, 페이지당 **최대 11문서**(화면에 10개 표시)
- 비용이 큰 부분은 화면별이 아니라 **로그인 직후 켜 두는 전역 구독**(특히 `shops` 전체)

---

## 1. 실시간 감시(snapshots) vs 1회 읽기(get)

| 화면 / 영역 | 무엇을 보나 | 방식 | Firestore 경로 | 비고 |
|-------------|-------------|------|---------------|------|
| Explore·홈 **상품/리조트 카드** | 별점·리뷰 수·좌석·상품 | **실시간 감시** (로그인 시 구독) | `shops` 컬렉션 전체 | 카드마다 get 없음. 샵 문서 안 `products[]`·집계 필드 사용 |
| **리조트/상품 상세** (본문·예약 UI) | 상품 목록·좌석·견적 | 위와 동일 캐시 | (추가 쿼리 없음) | `shops/{id}.get()` 안 함 |
| **후기 목록** (상세 하단) | 후기 글·세부 칩 | **1회 get** | `shops/{id}/reviews` (최신순, limit 11) | 실시간 감시 **없음**. “더 보기”도 get |
| 후기 **작성** 화면 | — | 목록 읽기 없음 | 저장 시 트랜잭션 get(샵·예약) | 목록 비용과 무관 |
| 로그인 후 백그라운드 | 유저·로그·예약·커뮤니티·가격 | **실시간 감시** | 아래 표 참고 | Explore와 무관하지만 세션 비용에 포함 |

### 로그인 후 켜 두는 실시간 감시 목록 (일반 다이버)

| 구독 | 경로 | 첫 스냅샷 대략 읽기 |
|------|------|---------------------|
| `watchShopStats` | `shops` 전체 | **S** (샵 문서 수) |
| `watchDiver` | `users/{uid}` + `users/{uid}/logs` | **1 + L** |
| `watchBookings` | `users/{uid}/bookings` | **B** |
| `watchCommunityPosts` | `posts` 전체 | **P** |
| `watchInstructorDiscount` | `settings/pricing` | **1** |
| **합(대략)** | | **S + L + B + P + 2** |

이후 구독이 살아있는 동안, 해당 컬렉션에서 **문서가 바뀔 때마다** 그 문서만큼 추가 읽기가 붙습니다.  
예: 어떤 샵의 좌석·후기 집계가 갱신되면 → 그 샵 문서 1회 추가 과금.

### 관리자·파트너(참고, 더 큼)

| 역할 | 추가 구독 |
|------|-----------|
| 관리자 | `users` 전체 스냅샷을 **두 갈래**(대기 강사·멤버), 샵별 `bookings` 감시 |
| 파트너(사업자) | 소유 샵 `shops/{ownedShopId}/bookings` 감시 |

Explore/상세 표와는 별개이나, 관리자 세션에서는 읽기 비용이 훨씬 큽니다.

### 관련 코드

- 실시간 샵: `lib/core/data/firestore_diver_repository.dart` → `watchShopStats()` → `_shops.snapshots()`
- 후기 get: 같은 파일 → `fetchShopReviewsPage()` → `query.get()`, `limit(pageSize + 1)`
- UI: `lib/features/explore/presentation/diver_reviews_section.dart` (`_pageSize = 10`)만 후기 서브컬렉션 조회
- 로그인 구독 연결: `lib/core/data/diver_store.dart` → `_bindDiver`

```text
로그인 → shops snapshots → 메모리 샵 캐시
                              ├→ 상품 카드 (추가 읽기 0)
                              └→ 상세 본문 (추가 읽기 0)
                                    └→ reviews get (페이지당 ≤11)
```

## 2. 화면을 열 때 문서 읽기 추정

기호: **S** = 샵 문서 수, **R** = 해당 샵 후기 문서 수, **L / B / P** = 내 로그·예약·게시글 수.

### Explore / 홈 카드만 열기

| 상황 | 추정 |
|------|------|
| 이미 로그인·샵 캐시 있음 | **추가 0** |
| 카드가 100장이어도 | 카드당 읽기 **0** (메모리) |

### 상세 화면 열기 (후기 섹션 포함)

| 상황 | 추정 |
|------|------|
| 상세 본문·상품·별 요약 | **추가 0** (샵 문서 캐시) |
| 후기 첫 페이지 | **min(R, 11)** — 후기 ≥10이면 보통 **11**, 적으면 **R**, 없으면 **0** |
| “더 보기” 한 번 | 또 **최대 11** |

예: 후기 25개 샵 상세 1회 오픈 → 대략 **11문서**. 더 보기 1회 → 누적 **~22**.

### 쉽게 보면

1. **카드·상세의 별/상품**은 화면 단위로 비싸지 않음 — 이미 받아 둔 샵 문서 재사용.
2. **후기 글**만 상세에서 페이지 get — 설계상 합리적.
3. 진짜 비용 후보는 **`shops` 전체를 실시간으로 계속 듣는 것** + (해당 시) **관리자 users/예약 구독**. 샵이 늘거나 좌석이 자주 바뀌면 읽기가 불어남.

## 3. 개선 아이디어 (아직 미적용)

우선순위는 “효과가 크고 / 체감 UX를 덜 깨는” 순입니다.

### A. `shops` 전체를 실시간으로 안 듣기 (가장 큰 후보)

- **지금**: 로그인 후 `shops.snapshots()` → 샵이 늘고 좌석이 자주 바뀌면 읽기 증가.
- **아이디어**:
  - Explore/홈: 주기적 또는 진입 시 `get` + 짧은 메모리/디스크 캐시
  - 상세/예약 직전만 해당 `shops/{id}`를 `get` 또는 짧은 구독
  - 좌석이 민감한 화면만 실시간, 목록은 수 분 캐시
- **트레이드오프**: 목록 별점·잔여석이 즉시 안 바뀜. UX 문구(“잠시 전 기준”) 필요할 수 있음.

### B. 관리자 구독 줄이기

- `users` 전체 스냅샷 2개 → 쿼리 + 페이지 get, 또는 관리 화면 들어올 때만 구독.
- 샵별 `bookings` 전 구독 → 선택 샵만, 또는 get + 새로고침.
- **효과**: 관리자 계정에서만 크지만, 콘솔 수치를 크게 줄일 수 있음.

### C. `posts` 전체 스냅샷

- 커뮤니티도 목록 진입 시 페이지 get, 또는 limit 쿼리로 바꾸면 세션 상시 비용을 줄임.
- 홈에 최신 글 미리보기가 필요하면 별도 “요약” 문서/필드 검토.

### D. 후기 목록 (이미 양호, 미세 조정)

- 현재 페이지 get은 유지해도 됨.
- 상세에서 후기 섹션이 화면 밖이면 **스크롤 진입 시 첫 페이지 로드**(지연 로딩)로 불필요한 상세 오픈 비용 감소.
- `limit(pageSize + 1)`은 hasMore용 — Firestore는 가져온 문서 수만큼 과금(최대 11). 필요하면 Aggregation/카운트 필드로 hasMore를 대체할 여지는 있으나 이득은 작음.

### E. 샵 문서 비대화 주의

- `products[]`·갤러리·소개가 한 문서에 있으면 `shops` 스냅샷 1회 = 큰 문서 전체 읽기.
- 장기적으로 상품 서브컬렉션 분리 + 목록용 요약 필드만 두면 대역폭·파싱도 줄어듦. (읽기 “건수”와는 별개로 전송량 이슈.)

### F. 측정부터

- Firebase Console → Usage에서 컬렉션별 읽기 추이 확인.
- 배포 전후로 “일반 다이버 로그인 → Explore → 상세 1곳” 시나리오를 로컬 로그로 세면 체감 개선을 검증하기 쉬움.

---

## 4. 하지 않아도 되는 것 (이번 점검 기준)

- 카드마다 후기 서브컬렉션을 읽는 구조는 **이미 없음** — 집계는 샵 문서에 내장.
- 후기 목록을 실시간으로 바꿀 필요는 없음(비용↑, 이득↓).
- 평균 별점 계산 방식·Storage 사진은 이 점검 범위 밖.
